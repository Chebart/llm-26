# Лабораторная 3. Диалоговый агент для PostgreSQL

Проект сравнивает собственного агента на LangGraph с готовым агентом Pi. Оба отвечают на вопросы по PostgreSQL, ищут документацию и выполняют SQL в учебной базе. Модель вызывается через Polza.AI. Langfuse показывает ход диалога, обращения к модели, инструменты, ошибки и сокращение контекста.

Модель для обоих агентов: `deepseek/deepseek-v4.1-flash`. Pi зафиксирован на версии 1.5.0. Все параметры находятся в `resources/config.toml`, тексты инструкций в `resources/prompts.toml`. Ключи и адреса окружения находятся в `.env`.

После рефакторинга старые артефакты и экспериментальные результаты удалены. Новый полный прогон ещё не выполнен. Описанные ниже выходные файлы появятся после соответствующих команд. Старые показатели качества и стоимости к текущему коду не относятся.

## Как запустить

Все команды выполняются в Bash внутри Ubuntu в WSL. В Docker Desktop включите интеграцию с этим дистрибутивом. Нужны Python 3.12, uv и Linux-версия Node.js от 22.19. Для Docker желательно выделить 8–12 ГБ RAM. Это рекомендация, а не измеренный минимум. Эмбеддинги считаются на CPU в 6 потоков, их веса занимают около 1 ГБ.

Откройте каталог лабораторной:

```bash
cd /mnt/d/projects/university/ITMO_labs/llm-26/projects/aa-chebykin/lab3
```

### Полный прогон одной командой

При уже установленном окружении и заполненном `.env`:

```bash
bash run.sh
```

`run.sh` является короткой точкой входа. Он выбирает Linux-окружение, добавляет локальный Node в PATH и вызывает `python -m core.cli run`. Последовательность стадий реализована функцией `run()` в `source/core/cli.py`. Аргументы скрипта передаются этой команде без изменения. Поэтому Bash не дублирует управление процессами и обработку ошибок из Python.

Скрипт поднимает Docker и ждёт готовности сервисов, применяет SQL-инициализацию, подготавливает данные и проверяет инструменты. Готовый индекс проверяется без пересчёта эмбеддингов. Затем скрипт запускает свой сервер инструментов, последовательно выполняет `custom-trim`, `custom-tiered` и `pi` и собирает сравнение в `results/09_report/`.

По умолчанию выделено 20 рублей на каждый профиль, всего 60 рублей на три запуска. Это лимит учёта расходов в приложении. Langfuse включается автоматически, ключи берутся из `.env`. Отдельный терминал для сервера инструментов не нужен. Если старый `serve-tools` ещё работает, сначала завершите его через Ctrl+C в его терминале.

Подготовка и проверки без платных обращений к чат-модели:

```bash
bash run.sh --prepare-only
```

Короткий пилот на одной задаче для всех трёх профилей, до 5 рублей на каждый:

```bash
bash run.sh --tasks docs-join --max-cost 5
```

Пилот сохраняется отдельно от benchmark и не заменяет полный датасет. Его сравнительный отчёт попадает в отдельный подкаталог `results/09_report/pilot-<id>/`.

При ошибке подготовки, неполном прогоне или разных условиях сравнения скрипт останавливается. Готовые результаты сохраняются. Повторный полный запуск создаёт новые прогоны, а не продолжает оплаченные реплики предыдущего. Для повтора одного профиля используйте ручную команду `evaluate` ниже. Запущенный скриптом сервер инструментов завершается при выходе и Ctrl+C. Его лог находится в `data/07_checks/tools-<id>.log`. Docker остаётся работать, чтобы можно было открыть Langfuse.

Веса и промежуточные данные остаются в прежнем `data/`. Скрипт `run.sh` сам добавляет локальный Node в PATH. Для ручных команд в новом терминале повторите экспорт PATH и присвоение `py` из примеров выше.

### Настройка и подготовка

Только если `.env` ещё нет:

```bash
"$py" -m core.cli init-env
```

Заполните `POLZA_API_KEY`, уникальный `LAB3_TOOL_TOKEN`, подключения к БД и ключи проекта Langfuse. Для записи traces включите `LANGFUSE_ENABLED=true`. Образец находится в `.env.example`. Файл `.env` не публикуйте.

```bash
docker compose up -d
docker compose ps
"$py" -m core.cli prepare
"$py" -m core.cli index
"$py" -m core.cli verify-data
"$py" -m core.cli validate

Точное новое число чанков нужно брать из этого вывода. `validate` проверяет датасет без LLM. `check-dataset` исполняет эталонные SQL-запросы. `smoke --retrieval` проверяет инструменты, включая ожидаемую SQL-ошибку и восстановление. Эти команды не вызывают платную чат-модель.

```bash

```

Langfuse открывается на `http://localhost:3000`. В локальном compose настроен проект `postgres-agents`. Ключи SDK должны принадлежать этому проекту. На чистой установке проверьте параметры начального пользователя в compose и задайте собственные значения перед использованием вне локальной машины.

### Диалог

```bash

```

Сервис инструментов слушает `127.0.0.1:8765`. Оставьте терминал открытым. В основном терминале создайте учебную сессию и запустите одного из агентов:

```bash

"$py" -m core.cli chat --profile custom-tiered --session defense-custom-01
```

Для Pi:

```bash

### Эксперименты и проверки кода

Полное сравнение выполняется в конце работы. Каждая команда имеет предел расходов 20 рублей. Это три отдельных бюджета, а не общий предел на все команды:

```bash
trim=$("$py" -m core.cli evaluate --profile custom-trim --max-cost 20 | tail -n 1)
tiered=$("$py" -m core.cli evaluate --profile custom-tiered --max-cost 20 | tail -n 1)
pi_run=$("$py" -m core.cli evaluate --profile pi --max-cost 20 | tail -n 1)
"$py" -m core.cli compare "$trim" "$tiered" "$pi_run"
```

Перед оплатой сначала нужен небольшой пилот с `--tasks` и меньшим бюджетом. Идентификаторы берите из `resources/tasks.json`. CLI может остановить запуск раньше бюджета, если остатка недостаточно для резерва следующей реплики.

`compare` не обращается к модели. Команда принимает три конкретных каталога, а не выбирает случайный последний запуск. Она создаёт `results/09_report/comparison.json`, сравнительные таблицы в `report.md`, кандидатов для разбора в `error_analysis.md` и полные записи этих случаев в `error_cases.json`. При разных условиях или неполных прогонах отчёт явно помечается предварительным. Если одна из команд оценки завершилась с ошибкой, сначала изучите её лог и сохранённый частичный отчёт, затем повторите только необходимый запуск.

Локальные проверки не требуют платных запросов:

```bash
"$py" -m ruff check source/core
"$py" -m ruff format --check source/core
node pi/node_modules/typescript/bin/tsc --project pi/tsconfig.json --noEmit
"$py" -m pytest source/tests/test_core_refactor.py -q
```

Тесты по просьбе автора исключены из Git. На новом клоне локального файла тестов не будет.

## 1. Откуда берутся данные

Задача агента состоит из двух частей. Документация объясняет поведение PostgreSQL. Учебная SQL-база позволяет проверить ответ действием. Нельзя считать фрагмент документации подтверждением того, что конкретный SQL-запрос уже исполнился.

Общий порядок:

```text
[01 PDF] -> [02 Markdown] -> [03 Очистка] -> [04 Чанки]
                                                 |
                                                 v
[06 Диалог + SQL] <--- [Поиск] <--- [05 Векторы + BM25]
        |
        v
[07 Проверки] -> [08 Эксперименты и разбор ошибок]
```

Схемы в README выполнены обычным текстом. Они отображаются без поддержки Mermaid.

Источник: `https://repo.postgrespro.ru/doc/pgsql/17.11/ru/postgres-A4.pdf`. Полный PDF сохраняется в `data/01_pdf/`. В обработку входят физические страницы 30–89 включительно. Номер физической страницы означает её позицию в PDF, а не напечатанный номер в колонтитуле.

Перед обработкой проверяется контрольная сумма PDF. Она позволяет убедиться, что скачан именно нужный файл. Ожидаемое значение задано в `resources/config.toml`. При несовпадении обработка останавливается.

На защите откройте PDF на физической странице 59. Затем используйте `pg17-p0059` во всех следующих стадиях. Так связь исходника с результатом будет наглядной.

## 2. Как PDF превращается в Markdown

`prepare` передаёт каждую выбранную страницу в PyMuPDF4LLM. OCR отключён, используется текстовый слой PDF. Результат до очистки сохраняется отдельным файлом `data/02_converted/pg17-p0059.md`.

Затем `normalize_markdown` выполняет следующие действия:

- приводит Unicode к NFC
- убирает мягкие переносы
- заменяет неразрывные пробелы обычными
- удаляет пробелы в конце строк
- приводит переводы строк к одному формату и сокращает избыток пустых строк

Результат сохраняется в `data/03_cleaned/pg17-p0059.md`. Исходный Markdown остаётся рядом на предыдущей стадии. Семантического переписывания текста моделью нет. Сложная таблица в PDF может конвертироваться неидеально, очистка не восстанавливает её смысл автоматически.

Для демонстрации откройте два файла рядом в VS Code и сравните их с PDF. Все 60 страниц сохраняются по отдельности, поэтому не нужно искать нужное место в общем текстовом файле.

## 3. Как получаются чанки и что означает токен

Markdown сначала делится по заголовкам, затем рекурсивно по длине в токенах. Чанк не пересекает границу страницы. Ограничение равно 200 токенам, перекрытие соседних фрагментов равно 30. Эти значения задают компромисс между размером контекста и сохранением соседних предложений.

Токен является элементом словаря конкретного токенайзера. Это может быть слово, часть слова или знак. Число символов не равно числу токенов. Здесь используются два разных токенайзера:

| Задача | Токенайзер | Для чего нужен |
|---|---|---|
| Разбиение и эмбеддинги | Giga Embeddings | Не превышать лимит фрагмента перед кодированием |
| Окно собственного агента | DeepSeek V4.1 Flash | Оценивать реальный формат сообщений и инструментов |

Чанки находятся в `data/04_chunks/chunks.json`. У каждого сохранены `chunk_id`, `document_id`, физическая страница, URL источника, заголовки и текст. По этим полям можно найти исходную страницу для любого фрагмента. `manifest.json` рядом сохраняет параметры подготовки и число чанков.

`verify-data` записывает в `data/07_checks/pipeline.json` пример token IDs и token pieces для страницы 59, число специальных токенов и максимальную длину чанка. Специальные токены также входят в длину, проверяемую embedding tokenizer. Для защиты откройте JSON, найдите `pg17-p0059` и сопоставьте текст с предыдущей стадией.

## 4. Как устроен индекс и поиск

Для эмбеддингов используется `ai-sage/Giga-Embeddings-instruct-480M-0826`. Версия зафиксирована в конфигурации. Dense-вектор имеет 1024 координаты. Кодирование идёт на CPU, векторы нормализуются. Для запроса применяется инструкция из config, для документа кодируется сам текст.

Параллельно FastEmbed строит sparse-представление `Qdrant/bm25` с русской обработкой текста. Параметры: `k=1.2`, `b=0.75`, `avg_len=256`. Dense-поиск помогает находить близкий смысл, BM25 помогает с точными терминами и именами SQL-конструкций.

```text
Запрос -> Giga -> 40 dense-кандидатов  -+
                                      +-> RRF -> 5 фрагментов
Запрос -> BM25 -> 40 sparse-кандидатов -+
```

Qdrant хранит оба представления и payload в коллекции `lab3_postgres17`. RRF объединяет позиции документов в двух выдачах. Его score не является вероятностью правильного ответа.

После индексации в `data/05_index/` находятся:

| Файл | Содержание | Что показать |
|---|---|---|
| `index.json` | параметры индекса и число точек | связь индекса с подготовленным корпусом |
| `vectors.jsonl` | реальные dense и sparse векторы вместе с payload | первую строку и массив dense из 1024 чисел |
| `vector-export.json` | сведения об экспорте и число точек | полноту выгрузки |

```bash
"$py" -m core.cli search "GENERATED ALWAYS IDENTITY" --limit 5
"$py" -m core.cli export-index
```

`search` возвращает текст, UUID и страницу. `read_doc_page` позволяет после поиска прочитать всю очищенную страницу. Агент получает документацию через эти инструменты, весь PDF в системную инструкцию не помещается.

Повторный `prepare` проверяет manifest. Изменение параметров требует явного `prepare --rebuild`. Перестроение коллекции с удалением старых точек требует `index --reset`. Эти флаги не нужны для обычного чата.

## 5. Какие инструменты доступны агентам

Оба агента используют одну реализацию `ToolService` и одинаковые схемы аргументов:

| Инструмент | Действие | Подключение |
|---|---|---|
| `search_docs` | гибридный поиск по документации | MCP |
| `read_doc_page` | чтение страницы после поиска | MCP |
| `inspect_schema` | таблицы, колонки и связи учебной сессии | MCP |
| `execute_sql` | исполнение SQL и получение строк | native tool у своего агента, HTTP у Pi |
| `explain_sql` | план SQL-запроса | native tool у своего агента, HTTP у Pi |

MCP работает по Streamable HTTP на `/mcp/`. Клиент проходит initialize, получает список инструментов и вызывает их по протоколу. Это настоящий MCP, а не переименование обычной Python-функции. HTTP-эндпоинт `/tools` обслуживает оставшиеся инструменты Pi. Доступ защищён токеном.

Полный результат каждого инструмента записывается в `data/06_sessions/tool_results/<artifact-id>.json`. В файле есть аргументы результата, статус, ошибка, длительность и идентификатор вызова. При сокращении ответа ссылка на полный артефакт сохраняется. События сервиса находятся в `data/06_sessions/tools/events.jsonl`.

## 6. Как устроены SQL и Docker

Учебные таблицы: `customers`, `products`, `orders`, `order_items`. Процедура `public.seed_exercise()` создаёт их и заполняет исходными строками. Процедура работает с правами вызывающей роли.

Каждая сессия получает отдельную схему и LOGIN-роль вида `task_<20 hex>`. Идентификатор вычисляется из session ID. Пароль выводится через HMAC из токена сервиса и session ID. Это позволяет повторно подключаться к своей сессии без хранения отдельных паролей в артефактах.

SQL разбирается через pglast. Ограничены допустимые операции, `search_path`, время запроса и число возвращаемых строк. По умолчанию запросу отведено 5 секунд, выдача ограничена 100 строками. Ошибка возвращается агенту как результат инструмента, после чего он может исправить запрос. Отдельная схема защищает другие диалоги, ограничения не превращают произвольный SQL в безопасный публичный сервис для внешних пользователей.

В compose семь сервисов:

| Сервис | Назначение | Порт на хосте |
|---|---|---|
| PostgreSQL | одна СУБД с отдельными БД `lab3` и `langfuse` | 5433 |
| Qdrant | dense и sparse индекс | 6335 |
| Langfuse web | интерфейс и API наблюдений | 3000 |
| Langfuse worker | обработка событий и фоновых задач | внутренний |
| ClickHouse | аналитическое хранилище наблюдений | см. compose |
| Redis | очередь и кеш Langfuse | внутренний |
| MinIO | исходные события Langfuse | см. compose |

Web и worker выполняют разные роли в штатной архитектуре Langfuse v3. ClickHouse, Redis и MinIO нужны этому стеку, а не модельному шлюзу. Polza является внешним API, отдельного контейнера шлюза и локального прокси нет. Роли учебных сессий не имеют доступа к БД Langfuse.

Данные этих сервисов находятся в Docker volumes. Это отличается от демонстрационных JSON и Markdown в `data/`. Не применяйте `docker compose down -v` ради уборки результатов, такая команда удалит также служебные настройки Langfuse.

## 7. Как проходит ход диалога

```text
Пользователь -> журнал -> подготовка окна -> модель Polza
                                             |
                          +------------------+------------------+
                          |                                     |
                     tool calls                            готовый ответ
                          |                                     |
                     MCP или SQL -> результат -> журнал          v
                          |                                пользователь
                          +------> подготовка окна
```

Собственный агент реализован графом LangGraph. Сообщение пользователя добавляется в SQLite. Затем агент подготавливает окно, вызывает AsyncOpenAI с native tools и либо отвечает, либо исполняет инструменты. Результаты возвращаются модели. Цикл продолжается до ответа или лимита.

На одну реплику разрешены 12 шагов и 24 обращения к модели с учётом суммаризации. Общий срок составляет 240 секунд. Таймаут API равен 90 секундам, инструмента 30 секундам. SDK допускает один повтор API-запроса. При прерывании история восстанавливается так, чтобы не оставались незакрытые tool calls.

Полный журнал собственного агента сохраняется в `data/06_sessions/history.sqlite3`, таблица `events`. Поля связывают сообщения с сессией и ходом. Его можно открыть SQLite viewer в VS Code. События ручного чата записываются в отдельный `chat-*/events.jsonl`. Сам CLI печатает ответ, статус, usage, стоимость и задержку. Полный порядок tool calls удобнее показывать через Langfuse и локальные JSONL.

Pi запускается программно через RPC. `pi/extension.ts` регистрирует те же пять инструментов. Встроенные bash и файловые инструменты отключены для сравнимости. Модель и provider Polza задаются в Pi штатным конфигом, обращения к API идут напрямую. Служебные конфиги и история Pi находятся в `data/06_sessions/pi/<run-id>/`. `rpc.jsonl` показывает обмен с процессом, `sessions/` хранит его журнал, `billing.jsonl` сохраняет полученные сведения о стоимости.

## 8. Как ограничивается контекст

Журнал и окно являются разными объектами. Журнал сохраняет всю переписку. Окно содержит только сообщения, которые сейчас отправятся модели. Изменение окна не удаляет исходные сообщения из SQLite.

У собственного агента бюджет входа равен 8192 токенам, резерв ответа равен 2048. Используется официальный токенайзер выбранной чат-модели. Его шаблон учитывает роли, инструменты и служебные элементы. Название и версия токенайзера зафиксированы в конфигурации. Локальная длина умножается на 1.3. Это консервативная оценка до сверки с реальными запросами, а не измеренное число токенов сервера.

Polza возвращает фактические prompt и completion tokens в usage. Их нужно использовать для результатов эксперимента.

Пока окно помещается в бюджет, сокращение не выполняется. При превышении последовательно применяются уровни:

| Уровень | Что происходит | Вызов LLM |
|---|---|---|
| MessageTrim | старые завершённые ходы вытесняются из окна, сохраняется заданное число недавних ходов | нет |
| ToolResultPurge | подробности старых результатов заменяются компактной записью со статусом и ссылкой | нет |
| MessageCollapse | сокращается длинный текст старых сообщений | нет |
| LLMSummarize | старая история заменяется сводкой до 512 токенов | да |
| EmergencyLLMSummarize | сводка дополнительно сокращается до 256 токенов | да |

Текущая задача и связанные пары assistant tool call и tool response защищены от разрыва. При ошибке суммаризации используется детерминированный fallback. Если даже защищённые сообщения не помещаются, возникает понятная ошибка ContextOverflow.

Для каждого сработавшего сокращения собственного агента сохраняется `data/06_sessions/context/<turn-id>-<id>.json`. Там находятся окна до и после уровня, описание инструментов и итоговое окно. В событии указан путь к этому файлу. Так можно показать, какие конкретно факты исчезли. Неуспешная суммаризация записывает ошибку, но готовой сводки у неё нет. При окончательном переполнении сохранение завершённого окна не гарантируется.

Профиль `custom-trim` использует только первый уровень. `custom-tiered` использует все пять. Сравнение показывает цену более сложной обработки. Сжатие не гарантирует сохранность всех фактов. Удаление старой реплики может ухудшить ответ о ранее названном городе, а очистка tool result может вызвать повторный поиск.

Pi использует собственную суммаризацию и оценку токенов. Адаптер учитывает внутренний запас Pi при настройке порога. DeepSeek tokenizer собственного агента не подменяет счётчик Pi. Поэтому равный целевой бюджет сам по себе не делает их способы подсчёта идентичными.

## 9. Что сохраняет Langfuse

Langfuse нужен для наблюдения за выполнением. Он не выбирает инструменты и не исправляет ответы. Решения принимает модель в агентном цикле.

```text
Session: один диалог
  Trace: одна реплика пользователя
    context: подготовка окна
    generation: запрос к модели
    tool: вызов инструмента
      retrieval: найденные документы
    generation: следующий запрос
    scores: оценки ответа
```

Собственный агент пишет наблюдения через Python SDK. Pi использует provider hook и официальный OpenTelemetry SDK Langfuse. Hook видит обращения к модели, включая штатную суммаризацию Pi. Он прикрепляет generation к текущему ходу по trace ID и parent span ID. HTTP-прокси для этого не требуется.

В наблюдениях должны быть вход, выход, модель, параметры, usage, стоимость, задержка и ошибка. Идентификаторы связывают диалог, реплику, вызов инструмента и артефакт. По trace видно, искал ли агент документы, выполнил ли SQL и исправил ли ошибку.

Токены из ответа API являются измерением. Стоимость `cost_rub` из шлюза является фактическим биллингом. Расчёт по каталогу является оценкой и помечается отдельно. Если usage или стоимость отсутствуют, неизвестное значение нельзя считать нулём. Это особенно важно для оборванных запросов и Pi.

После очистки старые traces удалены из проекта. Новые примеры и скриншоты нужно получить в финальном прогоне. Проверка доставки искусственного события не подтверждает корректность всей интеграции с настоящей моделью.

## 10. Как устроен эксперимент

В `resources/tasks.json` содержатся 24 задачи, 53 пользовательские реплики, 45 оцениваемых реплик. Из них 10 задач оформлены диалогами. Есть поиск по документации, SQL, восстановление после ошибки и длинные сценарии, превышающие бюджет окна. Эталонных SQL-критериев 32. Их корректность проверяет `check-dataset`.

Для сравнения должны совпадать модель, provider, параметры генерации, инструменты, исходная SQL-база, датасет и целевой бюджет. Два варианта своего агента отличаются стратегией контекста. Pi отличается реализацией цикла и штатным сжатием.

Каждый запуск создаёт отдельный каталог `results/08_experiments/<label>/<run-id>/`. Метки `pilot`, `benchmark`, `stress` отделяют назначение запусков. Механические проверки с имитатором не должны попадать в каталог реальных benchmark-результатов.

| Артефакт | Что хранит |
|---|---|
| `manifest.json` | настройки запуска и сведения об исходных данных |
| `dataset.json` | точные формулировки и критерии выбранных задач на момент запуска |
| `turns.jsonl` | промпт, ответ, tool calls, context events и метрики каждой реплики |
| `scores.jsonl` | проверяемые оценки реплик |
| `tasks.json` | итог каждой целой задачи, её полнота, ошибки, токены, стоимость и ссылки на реплики |
| `events.jsonl` | локальное дерево событий и ошибок |
| `summary.json` | агрегаты запуска |
| `report.md` | читаемый отчёт |

Готовые реплики записываются сразу. Если запуск оборвался, частичные результаты сохраняются. Неполную задачу нельзя считать успешно выполненной только по первым ответам.

Оцениваются успешность задач и реплик, зависимость от истории, инструменты, precision/recall/MRR поиска, задержка, токены и стоимость. Сводки делятся по сложности и типу задачи. Автоматическая SQL-проверка может отвергнуть полезный ответ из-за дополнительной колонки или последнего вспомогательного SELECT, такие случаи требуют ручного разбора.

Итог задачи считается по всем её репликам. Незавершённый диалог не считается успешным. В Langfuse создаётся отдельный `task_result` в сессии диалога с оценками и идентификаторами traces его реплик. Наблюдение `dataset_run` содержит агрегаты всего прогона. Не начатые из-за бюджета задачи перечисляются отдельно и не маскируются под измеренные ответы.

`error_task_rate` показывает долю начатых задач, в которых произошла ошибка инструмента или остановка агента. Восстановленная SQL-ошибка тоже входит в этот показатель, хотя задача может остаться успешной. `terminal_error_task_rate` учитывает остановку ответа с ошибкой. `limit_task_rate` учитывает таймауты и ограничения шагов или обращений к модели. `error_or_limit_task_rate` объединяет эти случаи. Доля ошибочных реплик сохраняется отдельно. Знаменатель этих показателей состоит из начатых задач, число запрошенных задач и полнота прогона показываются рядом.

Актуальных измеренных результатов после очистки пока нет. После финального запуска `compare` подготовит таблицы по типам и сложности и все неудачные проверяемые реплики. Категории ошибок в нём являются подсказками для разбора, а не доказанными причинами. Нужно подтвердить по traces минимум пять неудачных задач каждого агента и минимум три категории ошибок, сохранить скриншоты и сформулировать выводы по измерениям. Если неудачных задач меньше пяти, отчёт явно сообщит об этом. В таком случае дополнительные стресс-проверки описываются отдельно от основного сравнения.

Проверьте, что в trace действительно есть неудачный вызов и последующий успешный. Если модель исправила запрос заранее, этот trace не доказывает восстановление после ошибки.

```

Для длинного сценария присвойте `$session` его идентификатор из `turns.jsonl` и повторите команду. Сообщения журнала сохраняются целиком, даже если их уже нет в окне модели.

Если нужен отдельный живой запуск длинного сценария, после `/exit` из чата и при работающем сервере выполните:

```bash
"$py" -m core.cli evaluate --profile custom-tiered --tasks long-memory-1 --label stress --max-cost 10
```

Этот запуск содержит несколько реплик одного диалога, использует платную модель и сохраняется отдельно от основного сравнения. Срабатывание конкретных уровней зависит от реальной истории. Не утверждайте, что все пять уровней сработали, если этого нет в событиях.

Итоговые таблицы находятся в `results/09_report/report.md`, случаи ошибок в `results/09_report/error_analysis.md`. В Langfuse откройте выбранную сессию, раскройте trace реплики, iteration, generation и tool. Для поиска покажите вложенный retrieval со списком чанков. Для целой задачи покажите `task_result`, для прогона `dataset_run`. У Pi отдельно покажите generation суммаризации, если она сработала в выбранном длинном сценарии.

Завершив демо, в первом терминале остановите сервер через Ctrl+C. Docker можно оставить работающим для просмотра Langfuse.

Для сдачи понадобится отдельный набор материалов защиты. `data/` и `results/` исключены из Git вместе с ключами, весами и кешами. Сформируйте архив промежуточных стадий и выбранных результатов либо отдельно согласуйте публикацию небольшого отчёта со скриншотами. Наличие файлов на своём компьютере не означает, что преподаватель получит их при клонировании репозитория.

## 12. Как хранить новые данные

Корпус хранится по фиксированным стадиям 01–05. Старые варианты не копируются в новые каталоги при каждом запуске. Изменение параметров сопровождается явным rebuild и новым manifest.

Диалоги и их доказательства находятся в `06_sessions`, проверки в `07_checks`, реальные эксперименты в `08_experiments`. Кеши и зависимости не смешиваются с результатами. Временные проверки записывайте в системный временный каталог, а в проекте оставляйте только полезный итог.

При очистке 6 ноября удалены предыдущий корпус, старые отчёты, архивы отладки, журналы диалогов и инструментов. Учебные SQL-сессии и коллекция Qdrant сброшены. Старый неиспользуемый volume `lab3_langfuse_pg` удалён. Рабочие пользователи и ключи Langfuse сохранены. Локальная ведомость файловой очистки находится в `data/07_checks/cleanup.json`.

Не удаляйте `data/models`, `data/runtime/node`, `.venv-wsl` и `pi/node_modules` ради очистки эксперимента. Они содержат установки, которые нужны для следующего запуска. Не удаляйте Docker volumes других лабораторных.
